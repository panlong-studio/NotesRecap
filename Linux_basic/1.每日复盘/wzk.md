## 四、传输层（重要）

### 1. TCP协议

- #### TCP 的核心特性

  - **面向连接**：在数据传输前，必须通过“三次握手”建立连接；传输结束后，通过“四次挥手”释放连接。
  - **可靠传输**：
    - **确认应答 (ACK)**：接收方收到包后会回传确认。
    - **超时重传**：发送方如果没收到 ACK，会重新发送数据。
    - **序列号 (Sequence Number)**：解决包失序问题，接收方根据序号重新组装数据。
    - **去重**：如果收到重复的数据包，接收方会自动丢弃。
  - **流量控制 (Flow Control)**：通过“滑动窗口”机制，确保发送方不会发得太快导致接收方处理不过来。
  - **拥塞控制 (Congestion Control)**：当网络环境变差时，TCP 会主动降低发送速率，防止网络崩溃（如：慢启动、拥塞避免等算法）。
  - **全双工通信**：连接建立后，双方可以同时进行收发。

- ### TCP可靠传输的实现

  #### 1. 确认应答与序列号  (ACK & Sequence Number)

  这是可靠性的基石。

  - **序列号 (Seq)**：TCP 给发送的每一个字节都进行编号。接收方根据序列号可以对乱序到达的数据进行**排序**，并能识别出**重复数据**。
  - **确认应答 (ACK)**：接收方收到数据后，会返回一个确认号（Ack），告诉发送方：“我已经收到了序号 X 之前的所有数据，下次请从 X+1 开始发”。

  #### 2. 超时重传 (Retransmission)

  如果在规定的时间内（RTT，往返时间），发送方没有收到接收方的 ACK 确认，它会认为该报文段已丢失，并**重新发送**该数据。这保证了即使网络丢包，数据最终也能到达。

  #### 3. 连接管理 (Connection Management)

  通过**三次握手**建立连接和**四次挥手**释放连接。

  - 这确保了通信双方在传输数据前已经初始化好了序列号，并确认对方具备收发数据的能力。
  - 最后的 `TIME_WAIT` 状态（2MSL）确保了所有旧的残留报文在网络中消失，不会干扰新连接。

  #### 4. 流量控制 (Flow Control) —— 利用滑动窗口

  为了防止发送方发得太快，导致接收方缓冲区溢出。

  - 接收方会在 ACK 报文中告诉发送方自己的**接收窗口大小 (Window Size)**。
  - 发送方根据这个窗口大小调整发送速率。如果接收方缓冲区满了，发送方会停止发送，直到接收方腾出空间。

  #### 5. 拥塞控制 (Congestion Control)

  流量控制是端到端的，而拥塞控制是**全局性**的。它防止过多的数据注入网络，导致路由器崩溃或网络拥堵。

  - **慢启动**：初始发送量小，呈指数级增长。
  - **拥塞避免**：到达阈值后改为线性增长。
  - **快重传与快恢复**：当收到连续三个重复的 ACK 时，立即重传丢失包，而不必等待超时，从而快速恢复传输。

- ### 三次握手建立连接

  #### 一、 TCP 三次握手：建立连接

  TCP 是**面向连接**的协议，在传输数据前，双方必须通过“三次握手”来确认彼此的收发能力正常，并同步序列号。

  #### 关键参数说明

  | 参数    | 含义                                                 |
  | :------ | :--------------------------------------------------- |
  | **SYN** | 同步位，值为 1 表示这是一个建立连接的请求            |
  | **ACK** | 确认位，值为 1 表示确认号有效                        |
  | **Seq** | 序列号，标识本报文段第一个字节的编号                 |
  | **Ack** | 确认号，表示期望收到对方下一个报文段的第一个字节序号 |

  #### 1. 握手流程

  - **第一次握手：客户端---> 服务器**

    - 客户端发送一个连接请求报文。
    - **标志位**：同步位 `SYN=1`。
    - **序列号**：随机生成一个初始序号 `seq=x`。
    - **状态**：客户端进入 `SYN-SENT`（同步已发送）状态。

  - **第二次握手：服务器<---客户端**

    - 服务器收到请求，如果同意连接，则向客户端发送确认报文。
    - **标志位**：`SYN=1` 且 `ACK=1`。
    - **序列号/确认号**：服务器随机生成序号 `seq=y`，同时设置确认号 `ack=x+1`（表示收到了客户端的 x，希望下次收到 x+1）。
    - **状态**：服务器进入 `SYN-RCVD`（同步收到）状态。

  - **第三次握手：客户端 ---> 服务器**

    - 客户端收到服务器的确认后，最后一次向服务器发出确认。

    - **标志位**：`ACK=1`。

    - **序列号/确认号**：`seq=x+1`，`ack=y+1`。

    - **状态**：双方均进入 `ESTABLISHED`（已建立连接）状态。

               |                                                    |

      ​         |                                                    |

      ​         |             [ 1. SYN, seq=x ]          |
        SYN_SENT --------------------------------------------------> LISTEN
      ​         |                                                    |

      ​         |                                                    |

      ​         |                                                 SYN_RCVD
      ​         |          [ 2. SYN, ACK, seq=y, ack=x+1 ]           |
      ESTABLISHED <--------------------------------------------------
      ​         |                                                    |

      ​         |                                                    |

      ​         |             [ 3. ACK, seq=x+1, ack=y+1 ]           |
      ​         | --------------------------------------------------> ESTABLISHED
      ​         |                                                    |
      ​    (Connection Established)                         (Connection Established)

      | **握手次数** | **动作类型**     | **关键标识位**                       | **目的**                   | **证明的能力**        |
      | ------------ | ---------------- | ------------------------------------ | -------------------------- | --------------------- |
      | **第一次**   | Client -> Server | `SYN=1`, `seq=x`                     | 客户端请求建立连接         | 客户端：发送正常      |
      | **第二次**   | Server -> Client | `SYN=1`, `ACK=1`, `ack=x+1`, `seq=y` | 服务端同意连接并也请求连接 | 服务端：接收/发送正常 |
      | **第三次**   | Client -> Server | `ACK=1`, `ack=y+1`, `seq=x+1`        | 客户端确认服务端的连接请求 | 客户端：接收正常      |

  #### 2. 为什么要“三次”？（核心逻辑）

  - **确认双方收发能力**：
    - 第一次：服务器确认了“对方发能力”和“我收能力”正常。
    - 第二次：客户端确认了“我发、我收”和“对方发、对方收”全部正常。
    - 第三次：服务器确认了“我发能力”和“对方收能力”正常。

  ##### **为什么是三次而不是两次？**

   防止**已失效的连接请求报文段**突然又传送到了服务端。

  - 如果是两次：客户端发的第一个 SYN 阻塞了，于是发了第二个 SYN 并建立了连接。数据传完断开了，结果第一个 SYN 终于到了。服务端以为是新连接，直接回复 ACK 建立连接，但客户端其实根本不理会，导致服务端资源浪费。
  - 三次握手下，服务端发完 ACK 后，还需要客户端再确认一次。如果客户端不确认，连接就不会真正建立。

  ### 二、 TCP 四次挥手：释放连接

  由于 TCP 是**全双工**的，即双方都可以同时发送和接收数据，因此关闭连接时需要双方都分别完成“关闭”动作。

  #### 1. 挥手流程

  - **第一次挥手：客户端 ---> 服务器**

    - 客户端打算关闭连接，发送一个释放报文。
    - **标志位**：终止位 `FIN=1`。
    - **状态**：客户端进入 `FIN-WAIT-1` 状态。

  - **第二次挥手：服务器 <--- 客户端**

    - 服务器收到 `FIN`，回复一个确认报文。
    - **标志位**：`ACK=1`。
    - **状态**：服务器进入 `CLOSE-WAIT`（等待关闭）状态。**此时 TCP 连接处于“半关闭”状态**——客户端不再发数据，但服务器如果还有没发完的数据，客户端仍需接收。

  - **第三次挥手：服务器 <--- 客户端**

    - 服务器数据发送完毕，主动向客户端发送释放报文。
    - **标志位**：`FIN=1`。
    - **状态**：服务器进入 `LAST-ACK`（最后确认）状态。

  - **第四次挥手：客户端 ---> 服务器**

    - 客户端收到 `FIN` 后，必须发出最后的确认。

    - **标志位**：`ACK=1`。

    - **状态**：客户端进入 `TIME-WAIT` 状态。经过 **2MSL**（最大报文生存时间）后，客户端才进入 `CLOSED` 状态。

      | ------------ | ---------------- | ------------------------- | ----------------------------------------------- |
      | **第一次**   | Client -> Server | `FIN=1`, `seq=u`          | 客户端：我没数据发了，准备关了。                |
      | **第二次**   | Server -> Client | `ACK=1`, `ack=u+1`        | 服务端：我知道了，但我可能还没发完，你等会。    |
      | **第三次**   | Server -> Client | `FIN=1`, `ACK=1`, `seq=w` | 服务端：我也发完了，现在可以彻底关了。          |
      | **第四次**   | Client -> Server | `ACK=1`, `ack=w+1`        | 客户端：OK，收到！(进入 TIME_WAIT 确认对方收到) |

  #### ① 为什么需要四次？

  因为 TCP 是**全双工**的。

  - 当客户端发出 `FIN` 时，仅仅代表客户端**不再发送数据**，但它依然可以**接收数据**。
  - 服务端收到 `FIN` 后，先回一个 `ACK` 表示“知道了”。此时服务端可能还有残留数据要发，只有等服务端也发完数据并发出 `FIN` 后，连接才算真正双向关闭。

  #### ② 为什么客户端最后要等待 2MSL？

  `MSL` 是报文最大生存时间。等待 2MSL 有两个原因：

  1. **确保最后的 ACK 能到达服务端**：如果第四次挥手的 `ACK` 丢了，服务端会重发第三次的 `FIN`。客户端在 2MSL 内如果再次收到 `FIN`，就知道 `ACK` 丢了，会再次重发。
  2. **防止“已失效的连接请求”**：让本连接持续时间内产生的所有报文都从网络中消失，避免新旧连接的数据包混淆。

### 2. UDP协议

##### UDP 的核心特点

- **无连接**：发送数据前不需要建立连接（没有三次握手），发送结束后也没有连接释放。
- **不可靠交付**：它只负责把数据包发出去，不保证数据是否到达，也不保证到达的顺序，更没有重传机制。
- **面向报文**：UDP 对应用层交付的报文，既不合并也不拆分，而是保留这些报文的边界。
- **无拥塞控制**：网络出现拥塞时，UDP 不会降低发送速率。这对于实时应用（如视频会议）非常重要，因为哪怕丢掉一些帧，也比整体延迟要好。
- **支持多种交互**：不仅支持一对一通信，还支持一对多（广播）、多对多（组播）。
- **首部开销小**：TCP 首部固定 20 字节，而 UDP 首部仅 **8 字节**。



### 3.TCP和UDP的直观对比

| **维度**     | **TCP**                                  | **UDP**                   |
| ------------ | ---------------------------------------- | ------------------------- |
| **连接**     | 面向连接                                 | 无连接                    |
| **可靠性**   | 可靠传输（无差错、不丢失）               | 不可靠（尽力而为）        |
| **传输方式** | 字节流（无边界）                         | 数据报（保留边界）        |
| **传输效率** | 较慢（首部大，有确认机制）               | 极快（首部仅 8 字节）     |
| **应用场景** | 网页 (HTTP)、文件传输 (FTP)、邮件 (SMTP) | 视频通话、直播、游戏、DNS |

## 一、大小端转换函数

### htonl / htons / ntohl / ntohs

**作用**：在主机字节序和网络字节序之间进行转换。

| 函数    | 作用                                |
| ------- | ----------------------------------- |
| `htonl` | 32位主机字节序 → 网络字节序（大端） |
| `htons` | 16位主机字节序 → 网络字节序         |
| `ntohl` | 32位网络字节序 → 主机字节序         |
| `ntohs` | 16位网络字节序 → 主机字节序         |

**入参**：

- `uint32_t hostlong`：32位主机字节序整数
- `uint16_t hostshort`：16位主机字节序整数

**返回值**：转换后的网络/主机字节序整数

**头文件**：`#include <arpa/inet.h>`

## 二、IP地址转换函数

### inet_addr

**作用**：将点分十进制IP地址字符串转换为网络字节序的32位整型数。

**入参**：

- `const char *cp`：点分十进制IP字符串，如 "192.168.1.1"

**返回值**：网络字节序的32位整型IP地址

**头文件**：`#include <arpa/inet.h>`

---

### inet_aton

**作用**：将点分十进制IP地址字符串转换为网络字节序的`in_addr`结构体。

**入参**：

- `const char *cp`：点分十进制IP字符串
- `struct in_addr *inp`：输出参数，存储转换后的IP地址

**返回值**：成功返回非0，失败返回0

---

### inet_ntoa

**作用**：将网络字节序的`in_addr`结构体转换为点分十进制IP字符串。

**入参**：

- `struct in_addr in`：网络字节序的IP结构体

**返回值**：点分十进制IP字符串（静态缓冲区，不可重入）

## 三、DNS解析函数

### getaddrinfo

**作用**：将主机名/域名解析为IP地址，返回地址信息链表。

**入参**：

- `const char *node`：主机名/域名/点分十进制IPv4/十六进制IPv6
- `const char *service`：服务名或端口号（可NULL）
- `const struct addrinfo *hints`：期望返回的信息类型（可NULL）
- `struct addrinfo **res`：输出参数，指向地址信息链表的指针

**返回值**：成功返回0，失败返回非0错误码

**头文件**：`#include <sys/types.h> #include <sys/socket.h> #include <netdb.h>`

---

### freeaddrinfo

**作用**：释放`getaddrinfo`返回的地址信息链表。

**入参**：

- `struct addrinfo *res`：要释放的地址信息链表头指针

## 四、TCP/UDP通用函数

### socket

**作用**：创建一个通信端点，返回文件描述符。

**入参**：

- `int domain`：协议族
  - `AF_INET`：IPv4
  - `AF_INET6`：IPv6
  - `AF_UNIX`：本地通信
- `int type`：套接字类型
  - `SOCK_STREAM`：TCP（流式）
  - `SOCK_DGRAM`：UDP（数据报）
- `int protocol`：具体协议（通常填0，自动选择）

**返回值**：成功返回非负整数（文件描述符），失败返回-1

**头文件**：`#include <sys/types.h> #include <sys/socket.h>`

**示例： int listen_fd=socket(AF_INET,SOCK_STREAM,0);**

---

### bind

**作用**：将套接字绑定到指定的IP地址和端口号。

**入参**：

- `int sockfd`：socket返回的文件描述符
- `const struct sockaddr *addr`：要绑定的地址结构（通用类型）
- `socklen_t addrlen`：addr结构体的长度（sizeof）

**返回值**：成功返回0，失败返回-1

**注意**：服务端必须bind，客户端可选（不绑则系统分配临时端口）

**示例：int ret=bind(listen_fd,(struct sockaddr *)&addr,sizeof(addr));**

---

### listen

**作用**：将套接字设置为监听状态，准备接受客户端连接。

**入参**：

- `int sockfd`：socket返回的文件描述符
- `int backlog`：全连接队列的最大长度

**返回值**：成功返回0，失败返回-1

**内部变化**：调用后内核会创建半连接队列和全连接队列

**示例：int ret=listen(listen_fd,10);**

---

### connect

**作用**：客户端向服务器发起连接请求（TCP三次握手）。

**入参**：

- `int sockfd`：socket返回的文件描述符
- `const struct sockaddr *addr`：目标服务器的地址结构
- `socklen_t addrlen`：addr结构体的长度

**返回值**：成功返回0，失败返回-1

**示例：int ret=connect(listen_fd,(struct sockaddr *)&addr,sizeof(addr));**

---

### accept

**作用**：从监听套接字的全连接队列中取出一个已完成的连接。

**入参**：

- `int sockfd`：监听套接字的文件描述符
- `struct sockaddr *addr`：输出参数，存储客户端的地址信息（可NULL）
- `socklen_t *addrlen`：传入传出参数，addr缓冲区的大小（可NULL）

**返回值**：成功返回一个新的已连接套接字文件描述符，失败返回-1

**注意**：如果全连接队列为空，accept会阻塞

**示例：int ret=accept(listen_fd,(struct sockaddr *)&client_addr,&len);**

---

### send

**作用**：通过TCP连接发送数据（只拷贝到内核缓冲区）。

**入参**：

- `int sockfd`：套接字文件描述符
- `const void *buf`：要发送的数据缓冲区
- `size_t len`：要发送的数据长度
- `int flags`：发送选项（通常为0）
  - `MSG_OOB`：发送紧急数据
  - `MSG_DONTROUTE`：不经过路由器

**返回值**：成功返回实际发送的字节数，失败返回-1

**示例：int cnt=send(conn_fd,"byebye",6,0);**

---

### recv

**作用**：从TCP连接接收数据（从内核缓冲区拷贝到用户空间）。

**入参**：

- `int sockfd`：套接字文件描述符
- `void *buf`：接收数据的缓冲区
- `size_t len`：缓冲区长度
- `int flags`：接收选项
  - `MSG_PEEK`：查看数据但不从缓冲区移除
  - `MSG_WAITALL`：等待所有数据
  - `MSG_DONTWAIT`：非阻塞模式

**返回值**：成功返回实际接收的字节数，连接关闭返回0，失败返回-1

**示例：int cnt=recv(conn_fd,buf,sizeof(buf),0);**

##### **TCP 三次握手 + 函数调用流程**

```
1. 客户端：socket()           → 创建 socket 端点，返回 socketFd
                              （内核创建 socket 对象，包含输入/输出缓冲区）

2. 客户端：connect()          → 向服务器发送 SYN 报文（第一次握手）
                              参数：sockfd, 服务器地址, 地址长度
                              - 客户端进入 SYN_SENT 状态

3. 服务器：socket()           → 创建监听 socket 端点
4. 服务器：bind()             → 绑定 IP 地址和端口号
5. 服务器：listen()           → 设置监听，创建半连接队列和全连接队列
                              - 服务器进入 LISTEN 状态

6. 服务器收到 SYN 后          → 内核自动回复 SYN+ACK 报文（第二次握手）
                              （无需应用程序调用函数）
                              - 服务器进入 SYN_RCVD 状态

7. 客户端收到 SYN+ACK 后      → 内核自动回复 ACK 报文（第三次握手）
                              （无需应用程序调用函数）
                              - 客户端进入 ESTABLISHED 状态

8. 服务器收到 ACK 后          → 连接进入全连接队列
                              - 服务器进入 ESTABLISHED 状态

9. 服务器：accept()           → 从全连接队列取出已完成的连接
                              返回新的已连接套接字 connectFd

10. 双方：send() / recv()     → 通过已连接套接字进行数据传输

11. 双方：close()             → 关闭连接（触发四次挥手）
```

---

##### TCP 四次挥手 + 函数调用流程

```
1. 主动方（如客户端）调用 close()  → 发送 FIN 报文（第一次挥手）
                                    - FIN=1, Seq=u
                                    - 主动方进入 FIN_WAIT_1 状态
                                    - 函数：close(sockfd)

2. 被动方（如服务器）收到 FIN 后    → 内核自动回复 ACK 报文（第二次挥手）
                                    - ACK=1, Ack=u+1
                                    - 被动方进入 CLOSE_WAIT 状态
                                    - 主动方收到 ACK 后进入 FIN_WAIT_2 状态
                                    - 函数：无（内核自动完成）

3. 被动方调用 close()              → 发送 FIN 报文（第三次挥手）
                                    - FIN=1, ACK=1, Seq=v, Ack=u+1
                                    - 被动方进入 LAST_ACK 状态
                                    - 函数：close(connectFd)

4. 主动方收到 FIN 后               → 内核自动回复 ACK 报文（第四次挥手）
                                    - ACK=1, Ack=v+1
                                    - 主动方进入 TIME_WAIT 状态（等待 2MSL）
                                    - 被动方收到 ACK 后进入 CLOSED 状态
                                    - 函数：无（内核自动完成）

5. 等待 2MSL 后                    → 主动方进入 CLOSED 状态
                                    - 函数：无（内核自动完成）
```

## 五、I/O多路复用函数



### 一.select

* 核心工作原理

`select` 通过维护三个独立的 **位图 (bitmap)**（分别是读、写、异常集合）来监控 fd。

1. **用户态设置**：开发者将感兴趣的 fd 加入对应的集合（`fd_set`）。
2. **内核态轮询**：调用 `select` 函数后，进程进入阻塞，内核开始轮询这些集合中的所有 fd。
3. **返回通知**：当有 fd 就绪或超时，`select` 返回。此时内核会修改位图，只保留就绪的 fd，其余位清零。
4. **应用层遍历**：开发者必须遍历整个集合，用 `FD_ISSET` 判断哪个 fd 真正活跃

`

---

### FD_ZERO / FD_SET / FD_CLR / FD_ISSET

**作用**：操作fd_set集合。

| 函数                            | 作用                       |
| ------------------------------- | -------------------------- |
| `FD_ZERO(fd_set *set)`          | 清空集合                   |
| `FD_SET(int fd, fd_set *set)`   | 向集合中添加fd             |
| `FD_CLR(int fd, fd_set *set)`   | 从集合中删除fd             |
| `FD_ISSET(int fd, fd_set *set)` | 检查fd是否在集合中（就绪） |

---

### select的缺点

#### 1. 数量限制 (硬伤)

- **描述**：`select` 使用位图（bitmap）来保存文件描述符，其大小由内核常量 `FD_SETSIZE` 限制（通常为 **1024**）。
- **影响**：对于需要支持上万甚至百万并发连接的现代服务器（如 Web 服务器、网关），1024 的上限远远不够，且无法通过简单修改代码绕过。

#### 2. 内存拷贝开销 (高频损耗)

- **描述**：由于内核不会保存监听状态，**每次**调用 `select` 都必须将整个 `fd_set` 从用户态**全量拷贝**到内核态。
- **影响**：当监控的连接数增加时，这种频繁的内存拷贝会消耗大量 CPU 资源，导致系统吞吐量下降。

#### 3. 编程模型冗余 (易用性差)

- **描述**：`select` 的 `fd_set` 是**参数与返回值合一**的。内核在返回时会修改传入的集合，将未就绪的 fd 清空。
- **影响**：用户程序必须在每次调用 `select` 前，手动重新初始化（重新 `FD_SET`）所有的文件描述符，增加了代码复杂度。

#### 4. 遍历效率低下 (性能瓶颈)

- **描述**：这是最核心的性能问题。`select` 返回后，它只告诉你有“几个”fd 就绪了，但**没告诉你是“哪几个”**。

- **影响**：应用程序必须以 $O(n)$ 的复杂度**线性遍历**整个 `fd_set`，通过 `FD_ISSET` 逐个检查，才能找到真正活跃的连接。

  > **痛点**：如果你监控了 1024 个连接，但只有一个连接有数据，你依然要循环 1024 次。

### 二.epoll



### 1、 核心工作原理

`epoll` 在内核中维护了两个关键的数据结构，解决了传统 `select` 轮询效率低下的问题：

- **红黑树 (RB-Tree)**：用于存储所有需要监控的文件描述符。
  - **优势**：支持高效的增、删、改、查（时间复杂度为 $O(\log n)$）。用户只需通过 `epoll_ctl` 注册一次，内核就会持久保存，不需要每次调用都重复拷贝。
- **就绪链表 (Ready List)**：双向链表，只存放当前发生了 I/O 事件（如数据到达）的描述符。
  - **优势**：当某个 Socket 活跃时，内核通过**回调机制**将其直接放入此链表。应用层调用 `epoll_wait` 时，内核直接返回该链表，无需遍历整个监控集合。



### 2、epoll 的特点与优势

epoll 是 Linux 内核提供的高性能 I/O 多路复用机制，特别适合 **大量并发连接但只有少量活跃** 的场景。

| 特点                      | 说明                                                       |
| :------------------------ | :--------------------------------------------------------- |
| **无文件描述符上限**      | 仅受系统内存限制（`/proc/sys/fs/file-max`）                |
| **内核态常驻 epoll 对象** | 监听集合和就绪集合分离，避免重复拷贝                       |
| **监听集合使用红黑树**    | 高效管理大量 fd，支持 O(log n) 的增删改查                  |
| **就绪集合使用双向链表**  | 只返回活跃的 fd，无需轮询所有监听 fd                       |
| **回调机制**              | 当 fd 状态变化时，内核通过回调主动通知 epoll，而非被动轮询 |
| **输入输出分离**          | 监听集合不会被修改，无需反复初始化                         |



### 3、eloll函数解析

### epoll_create

**作用**：创建一个epoll实例，返回epoll文件描述符。

**入参**：

- `int size`：历史遗留参数，只需填大于0的值（如1）

**返回值**：成功返回epoll文件描述符，失败返回-1

**头文件**：`#include <sys/epoll.h>`

**示例：int epfd=epoll_create(1);**

---

### epoll_ctl

**作用**：控制epoll实例，添加/修改/删除要监视的文件描述符。

**入参**：

- `int epfd`：epoll_create返回的文件描述符
- `int op`：操作类型
  - `EPOLL_CTL_ADD`：添加
  - `EPOLL_CTL_MOD`：修改
  - `EPOLL_CTL_DEL`：删除
- `int fd`：要操作的文件描述符
- `struct epoll_event *event`：事件结构体（删除时可为NULL）

**返回值**：成功返回0，失败返回-1

**示例： int ret = epoll_ctl(epfd,EPOLL_CTL_ADD,STDIN_FILENO,&evt);**

---

### epoll_wait

**作用**：等待epoll实例上的事件就绪。

**入参**：

- `int epfd`：epoll文件描述符
- `struct epoll_event *events`：输出参数，存储就绪事件数组
- `int maxevents`：events数组的最大长度
- `int timeout`：超时时间（毫秒），-1表示无限等待

**返回值**：成功返回就绪事件个数，失败返回-1

**示例：int nready = epoll_wait(epfd, lst, 2, -1);**

### 5、epoll 的触发模式

#### 1. 水平触发（LT，Level Triggered）

- **默认模式**
- **行为**：只要文件描述符上还有待处理的事件（如缓冲区还有数据），`epoll_wait` 就会持续通知
- **优点**：实现简单，不易出错
- **缺点**：可能会重复通知，需要应用程序自行判断是否处理完

```
// 水平触发示例：每次缓冲区有数据都会通知
event.events = EPOLLIN;  // 默认就是 LT
```

------

#### 2. 边缘触发（ET，Edge Triggered）

- **行为**：仅在文件描述符的状态发生变化时（如从不可读变为可读）通知一次
- **特点**：如果一次没有读完缓冲区中的数据，后续不会再次通知，直到有新数据到来
- **优点**：高效，减少了重复通知
- **缺点**：实现复杂，需要配合 while 循环 + 非阻塞 I/O

```
// 边缘触发设置
event.events = EPOLLIN | EPOLLET;
```



### 6、边缘触发与非阻塞 I/O 的配合

由于边缘触发只在状态变化时通知一次，如果一次没有读完所有数据，后续不会再次通知。因此需要：

1. **使用 while 循环读取**，直到读完全部数据
2. **使用非阻塞 `recv`**，防止最后一次读取时阻塞



### 7、epoll 工作流程总结

```
1. epoll_create()           → 创建 epoll 实例
2. epoll_ctl(ADD)           → 添加要监听的 fd（如 socket、stdin）
3. epoll_wait()             → 等待事件就绪
4. 遍历返回的 events 数组    → 处理就绪的 fd
   - 如果是监听 socket 就绪 → accept() 新连接，并 epoll_ctl(ADD)
   - 如果是已连接 socket    → recv() 读取数据
   - 如果是标准输入         → read() 读取输入并发送
5. 重复步骤 3-4
6. close(epfd)              → 关闭 epoll 实例
```



### 8、epoll vs select 对比

| 对比项             | select                 | epoll                        |
| :----------------- | :--------------------- | :--------------------------- |
| 文件描述符上限     | 1024（`fd_set`）       | 无限制（受内存限制）         |
| 内核实现           | 轮询扫描所有 fd        | 回调机制，只处理活跃 fd      |
| 用户态/内核态拷贝  | 每次调用都拷贝全量集合 | 创建时拷贝一次，后续增量更新 |
| 监听集合是否被修改 | 是，每次需要重新初始化 | 否，维护在内核红黑树中       |
| 适用场景           | 少量 fd                | 大量并发，少量活跃           |



### 9、重要注意事项

1. **epoll 是 Linux 特有的**，Windows 上对应 IOCP，macOS 上对应 kqueue
2. **边缘触发必须配合非阻塞 I/O**，否则可能导致阻塞或数据遗漏
3. **`epoll_wait` 返回的就绪事件数组是只读的**，应用程序不应修改其中的内容
4. **关闭 fd 时会自动从 epoll 实例中移除**，无需显式调用 `epoll_ctl(DEL)`
5. **`epoll_create` 的 `size` 参数已废弃**，只需填大于 0 的值
