# HTTP协议

​	我们可以把 HTTP 协议看作是**餐厅里的服务员**：你（客户端）向服务员下达点菜清单（请求），服务员将清单交给厨房，然后将做好的菜品（响应）端回给你。他本身不负责烹饪，只负责极其规范地“传话”和“端菜”。

​	作为一个及其重要的应用层协议,  HTTP的核心功能就是在网络上的客户端和服务器之间传输超文本数据，而这个传输过程最重要的就是构建HTTP请求和响应报文。(客户端发送给服务器的信息，称之为请求信息；服务器返回给客户端的信息称之为响应信息。一般情况下，我们也将发送的信息称之为报文。即HTTP请求报文和HTTP响应报文)

![HTTP协议](https://hixiaodong123.oss-cn-hangzhou.aliyuncs.com/typora/202504092035903.png#padding#600w)

## HTTP 的主要特点与特征

HTTP（HyperText Transfer Protocol，超文本传输协议）是用于从万维网服务器传输超文本到本地浏览器的传送协议。

1. **简单快速**：客户端向服务器请求服务时，只需传送请求方法和路径。由于 HTTP 协议简单，使得 HTTP 服务器的程序规模小，通信速度很快。
2. **灵活**：HTTP 允许传输任意类型的数据对象。正在传输的类型由 `Content-Type` 加以标记（如 HTML、JSON、图片、视频等）。
3. **无连接（Connectionless）**：无连接的含义是限制每次连接只处理一个请求。服务器处理完客户的请求，并收到客户的应答后，即断开连接（注：在 HTTP/1.1 中默认开启了 `Keep-Alive` 持久连接，以复用 TCP 连接，减少握手开销）。
4. **无状态（Stateless）**：HTTP 协议是无状态协议。这意味着协议对于事务处理没有记忆能力。服务器不知道客户端是什么状态，每次请求都是独立的。为了解决这个问题，引入了 **Cookie** 和 **Session** 技术来维持用户状态。

## HTTP 报文结构

HTTP 通信由两部分组成：**客户端的请求报文** 和 **服务端的响应报文**。

### 1. HTTP 请求报文 (Request)

请求报文由四个部分组成：**请求行、请求头、空行、请求正文（请求体）**。

- **请求行 (Request Line)**：包含三个字段：**请求方法**（如 GET、POST）、**请求 URL**、**HTTP 协议版本**。它们之间用空格分隔。
- **请求头 (Request Headers)**：由多行键值对组成，用于向服务器传递附加的客户端信息（如浏览器类型、支持的语言、主机地址等）。格式为 `Key: Value`。
- **空行 (Blank Line)**：请求头之后必须是一个空行（即一个回车换行符 `\r\n`），用来告诉服务器请求头到此结束。
- **请求正文 (Request Body)**：可选部分。通常在 POST 或 PUT 请求中使用，用于携带提交给服务器的数据（如表单数据、JSON 字符串）。GET 请求通常没有正文。

**请求报文示例：**

```http
GET / HTTP/1.1
Host: www.cskaoyan.com
Connection: keep-alive
Upgrade-Insecure-Requests: 1
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/110.0.0.0 Safari/537.36
Accept: text/html,application/xhtml+xml,application/xml;
Accept-Encoding: gzip, deflate
Accept-Language: zh-CN,zh;q=0.9,en;q=0.8
Cookie: __yjs_duid=1_94c0d6c26a48d04ztHBDp1OrzJxavJbibLH2u7JlFEirZPMlmtowns; 
```

```http
POST /login HTTP/1.1       <-- 请求行
Host: www.example.com      <-- 请求头开始
User-Agent: Mozilla/5.0 
Content-Type: application/json
Content-Length: 36         <-- 请求头结束
                           <-- 空行 (\r\n)
{"username":"admin","password":"123"} <-- 请求正文
```

### 2. HTTP 响应报文 (Response)

响应报文同样由四个部分组成：**状态行（响应行）、响应头、空行、响应正文（响应体）**。

- **状态行 (Status Line)**：包含三个字段：**HTTP 协议版本**、**状态码**（如 200, 404）、**状态描述（原因短语）**。
- **响应头 (Response Headers)**：由多行键值对组成，用于向客户端传递附加的服务器信息（如服务器软件类型、返回数据的类型、内容长度等）。
- **空行 (Blank Line)**：响应头之后必须是一个空行，标志着响应头信息的结束。
- **响应体 (Response Body)**：服务器返回给客户端的实际数据内容（如 HTML 文档、图片数据、JSON 格式的数据等）。

**响应报文示例：**

```HTTP
HTTP/1.1 200 OK            <-- 状态行
Server: nginx              <-- 响应头开始
Content-Type: application/json
Content-Length: 27         <-- 响应头结束
                           <-- 空行 (\r\n)
{"status":"success","id":1} <-- 响应体
```

## HTTP 方法与状态码

### 常见的 HTTP 方法

| **方法**   | **描述**                                                     |
| ---------- | ------------------------------------------------------------ |
| **GET**    | 请求获取指定的资源（主要用于读取数据）。                     |
| **POST**   | 向指定资源提交数据进行处理请求（如提交表单或上传文件），数据被包含在请求体中。 |
| **PUT**    | 向指定资源位置上传其最新内容（通常用于更新整体资源）。       |
| **DELETE** | 请求服务器删除指定的资源。                                   |

### 常见的 HTTP 状态码

状态码由三位数字组成，第一个数字定义了响应的类别：

- **1xx (信息性状态码)**：接收的请求正在处理。
- **2xx (成功状态码)**：请求正常处理完毕。常见：**200 OK**（请求成功）。
- **3xx (重定向状态码)**：需要进行附加操作以完成请求。常见：**301 Moved Permanently**（永久重定向）、**302 Found**（临时重定向）。
- **4xx (客户端错误状态码)**：服务器无法处理请求。常见：**403 Forbidden**（拒绝访问）、**404 Not Found**（资源不存在）。
- **5xx (服务器错误状态码)**：服务器处理请求出错。常见：**500 Internal Server Error**（服务器内部错误）、**502 Bad Gateway**（网关错误）。

## HTTP 与 HTTPS 的区别

HTTP 协议的数据是明文传输的，安全性较差。为了解决这个问题，引入了 **HTTPS (HyperText Transfer Protocol Secure)**。HTTPS 并非是一个全新的协议，而是 `HTTP + SSL/TLS`，即在 HTTP 的基础上加入了加密处理和认证机制。

| **维度**     | **HTTP**                                  | **HTTPS**                                                    |
| ------------ | ----------------------------------------- | ------------------------------------------------------------ |
| **安全性**   | 明文传输，数据极易被窃听和篡改。          | 密文传输（经过 SSL/TLS 加密），安全性高，可防止防窃听、篡改和冒充。 |
| **默认端口** | **80** 端口                               | **443** 端口                                                 |
| **证书需求** | 无需证书                                  | 需要向 CA（证书颁发机构）申请并配置数字证书。                |
| **连接过程** | 建立 TCP 连接（三次握手）后即可传输数据。 | 在 TCP 三次握手之后，还需要进行 **SSL/TLS 握手**建立加密信道，然后才能传输数据。 |
| **资源消耗** | 较小（仅 CPU 和内存的常规开销）。         | 较大（加解密过程会消耗更多的 CPU 计算资源和时间）。          |

## GET与POST的区别

​	GET 和 POST 是 HTTP 协议中最常用的两种请求方法。虽然它们底层都是基于 TCP/IP 协议传输数据，但在 HTTP 规范的设计意图和浏览器的实际应用中，它们有着非常明显的区别。

​	可以这样简单理解：**GET 就像是“向服务器索要数据”**（比如浏览网页、获取文章列表），而 **POST 就像是“向服务器提交数据”**（比如填写注册表单、上传文件）。

​	以下是它们的核心区别对比：

| **对比维度**             | **GET 请求**                                                 | **POST 请求**                                                |
| ------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **主要作用 (语义)**      | **获取资源**：从服务器请求指定的数据。                       | **提交数据**：向服务器发送数据以创建或修改资源。             |
| **数据传输位置**         | 附加在 **URL 的查询字符串**中（例如 `?name=admin&age=20`）。 | 包含在 **HTTP 请求体（Request Body）**中。                   |
| **数据长度限制**         | **有严格限制**。受限于浏览器和服务器对 URL 长度的限制（通常在 2KB 到 8KB 之间）。 | **无明显限制**。可以传输大量数据，具体限制取决于服务器配置。 |
| **安全性（相对）**       | **较低**。参数直接暴露在 URL 中，会保留在浏览器历史记录和服务器日志中，**绝对不能**用于传输密码等敏感信息。 | **较高**。数据放在请求体中，不会显示在 URL 里。*(注：POST 只是相对隐蔽，如果没有 HTTPS 加密，数据依然可以通过抓包被看到)*。 |
| **幂等性 (Idempotency)** | **是幂等的**。多次执行同一个 GET 请求，服务器的状态不会改变，返回的结果也是一样的。 | **非幂等**。多次执行同一个 POST 请求，可能会在服务器上创建多个不同的资源（例如重复提交订单）。 |
| **缓存与历史记录**       | 可以被浏览器**主动缓存**，会留在历史记录中，可以被收藏为书签。 | **默认不会被缓存**，不会留在历史记录中，不能被收藏为书签。   |
| **数据类型限制**         | 只允许传输 **ASCII 字符**。如果包含中文或特殊字符，需要进行 URL 编码（如 `%20`）。 | **没有限制**。支持二进制数据（如图片、视频）、JSON、XML、纯文本等格式。 |

# TCP协议

​	我们可以把 TCP 协议看作是一个**极其负责任的快递员**：他不仅要确保包裹送到（可靠性），还要保证包裹的顺序是对的（顺序性），甚至还会根据路况调整开车速度（拥塞控制）。

## TCP 协议的特点

1. **面向连接 (Connection-oriented) **：传输数据前必须先“握手”建立连接，就像拨通电话后才开始交谈。
2. **可靠传输 (Reliable) **：通过确认应答（ACK）、超时重传、错误校验等机制，确保数据不丢失、不重复、不乱序。
3. **全双工通信 (Full-duplex) **：连接的两端可以同时发送和接收数据。
4. **面向字节流 (Byte-stream) **：TCP 把数据看作无结构的字节流。它不关心应用程序发出的消息边界，而是根据自己的缓冲区大小来拆分或合并数据。（注意：**TCP 是“面向字节流”的，但它发送数据时又是以“报文段 (Segment)”为单位的**）
5. **流量控制与拥塞控制 **：通过“滑动窗口”防止发送方太快淹没接收方，通过“拥塞窗口”感知网络拥堵并调整发送速率。

## TCP 报文头结构

​	TCP 报文头紧跟在 IP 报文头之后，标准的头部长度是 **20 字节**（不含选项部分）。

![TCP头部格式](https://hixiaodong123.oss-cn-hangzhou.aliyuncs.com/typora/202504092043049.png#padding#600w)

| **字段名称**            | **长度 (bits)** | **主要功能简述**                                             |
| ----------------------- | --------------- | ------------------------------------------------------------ |
| **源端口/目的端口**     | 16 / 16         | 标识数据从哪个进程来，去往哪个进程（IP 负责找主机，端口负责找程序） |
| **序列号 (Seq)**        | 32              | 本报文段发送数据的第一个字节的编号，保证数据的**顺序**       |
| **确认号 (Ack)**        | 32              | 期望收到对方下一个报文段的第一个字节的编号                   |
| **首部长度 (数据偏移)** | 4               | 标识 TCP 首部长度（因为它可能有可变长度的“选项”）            |
| 保留位                  | 3               | 保留备用，通常置 0                                           |
| **标志位 (Flags)**      | 9               | 包含 URG, **ACK**, PSH, **RST**, **SYN**, **FIN**, NS, CWR, ECE，控制连接与传输行为 |
| **窗口大小 (Window)**   | 16              | 表示接收方当前还能接收多少字节，用于**流量控制**             |
| **校验和 (Checksum)**   | 16              | 用于检查 TCP 首部和数据在传输过程中是否出错                  |
| 紧急指针                | 16              | 标识紧急数据位置                                             |
| 选项                    | 可变            | 常见选项有：MSS (Maximum Segment Size)、窗口扩大因子、时间戳、SACK (Selective Acknowledgment) 等 |
| 填充                    | 可变            | 保证首部按 4 字节对齐                                        |

## 三报文握手（建立连接）

​	TCP（传输控制协议）是一种面向连接的、可靠的、基于字节流的传输层通信协议。在传输数据之前，必须先建立连接，也就是**三报文握手**；在数据传输结束后，必须释放连接，也就是**四报文挥手**。

​	三报文握手是客户端和服务端在正式传输数据前，同步彼此序列号和确认号，并交换TCP窗口大小信息的过程。

### 过程解析：

- **第一次握手：**客户端向服务端发送连接请求报文段，包含同步标志位 `SYN=1` 和一个随机生成的序列号 `seq=x`。此时客户端进入 **SYN-SENT**（同步已发送）状态。
- **第二次握手：**服务端接收到请求后，如果同意建立连接，则发送确认报文段。包含同步标志`SYN=1`，确认标志 `ACK=1`，确认号 `ack=x+1`，以及服务端自己随机生成的序列号 `seq=y`。此时服务端进入 **SYN-RCVD**（同步收到）状态。
- **第三次握手：**客户端收到服务端的确认后，再向服务端发送一个确认报文段。包含确认标志 `ACK=1`，确认号 `ack=y+1`，序号 `seq=x+1`。发送完毕后，客户端进入 **ESTABLISHED**（已建立连接）状态。服务端收到此确认后，也进入 **ESTABLISHED** 状态。至此，连接建立成功。4

### 为什么要三次握手？

1. **为了确认双方的收发能力：**
   - 第一次握手：服务端确认了“客户端的发送能力”和“服务端的接收能力”正常。
   - 第二次握手：客户端确认了“服务端的收发能力”和“客户端的收发能力”正常。但这还不够，服务端此时还不知道客户端的接收能力是否正常。
   - 第三次握手：服务端确认了“客户端的接收能力”正常。至此，双方都明确了彼此的收发能力是没问题的。

2. **防止已失效的请求报文导致资源浪费：** 假设只有两次握手，如果客户端发出的第一个连接请求报文段在网络节点中长时间滞留，客户端超时后会重传请求并完成通信。但此时那个“滞留”的旧请求突然到达服务端，服务端会误以为是新的连接请求，发送确认并单方面建立连接，从而导致服务端的资源被白白占用。

## 四报文挥手（断开连接）

当数据传输完毕，通信双方都可以主动发起断开连接的请求。

### 过程解析（以客户端主动断开为例）：

- **第一次挥手：**客户端认为数据发送完毕，向服务端发送连接释放报文段，包含结束标志 `FIN=1` 和序号 `seq=u`。客户端进入 **FIN-WAIT-1**（终止等待1）状态，停止发送数据。
- **第二次挥手：**服务端收到释放请求后，发出确认报文段，包含 `ACK=1`，确认号 `ack=u+1`，序号 `seq=v`。此时服务端进入 **CLOSE-WAIT**（关闭等待）状态。客户端收到该确认后，进入 **FIN-WAIT-2**（终止等待2）状态。
- **第三次挥手：** 服务端的数据也发送完毕后，向客户端发送连接释放报文段，包含 `FIN=1`，`ACK=1`，序号 `seq=w`，确认号 `ack=u+1`。服务端进入 **LAST-ACK**（最后确认）状态。
- **第四次挥手：** 客户端收到服务端的释放报文段后，发出确认报文段，包含 `ACK=1`，确认号 `ack=w+1`，序号 `seq=u+1`。客户端进入 **TIME-WAIT**（时间等待）状态。服务端收到确认后，立即进入 **CLOSED**（关闭）状态。客户端在经过 2MSL（最长报文段寿命的两倍）的时间后，也自动进入 **CLOSED** 状态。

## 为什么要四次挥手？

1. **保证最后一个 ACK 能够到达服务端：** 如果第四次挥手的 ACK 报文丢失，服务端会因为收不到确认而重传第三次挥手的 FIN 报文。客户端在这个 2MSL 时间窗内可以重新发送 ACK，确保服务端正常关闭。
2. **防止“脏数据”干扰新连接：** 经过 2MSL 时间，本次连接产生的所有报文段都会在网络中自然消亡，确保在下一个新的 TCP 连接中，不会出现旧连接遗留的失效报文段。

# UDP协议

​	我们可以把 UDP 协议看作是一个**性子急躁的广播员**（或者**发传单的人**）：他只管把信息通过大喇叭喊出去，或者把传单塞给你，至于你听没听清、有没有收到、顺序对不对，他一概不管。他追求的是极致的速度和实时性，而不是可靠性。

## UDP 协议的特点

1. **无连接 (Connectionless)**：发送数据之前不需要建立连接（没有三次握手），减少了开销和发送数据之前的时延。想发就发，非常迅速。
2. **首部开销极小**：UDP 的首部只有 8 个字节，相比于 TCP 的 20 个字节，其网络开销非常小。
3. **不可靠传输 (Unreliable)**：尽最大努力交付，不保证可靠交付。这意味着数据可能会丢失、重复或乱序，主机也不需要维持复杂的连接状态表。
4. **面向报文 (Message-oriented)**：UDP 对应用层交下来的报文，既不合并，也不拆分，而是直接保留这些报文的边界。添加完首部后就直接向下交付 IP 层（一次发送一个完整的报文）。
5. **无拥塞控制 (No Congestion Control)**：网络出现拥塞时，UDP 不会像 TCP 那样降低源主机的发送速率。这对某些对实时性要求极高的应用（如视频会议、直播、在线游戏）非常重要，因为它们宁愿丢弃一些画面帧，也不能接受严重的延迟。
6. **快速传输**：由于缺乏连接建立、确认响应、流量控制等机制，UDP可以更快速地传输数据（能不能到目的地是另外一件事）。
7. **支持多种交互通信**：TCP 只能是一对一的通信，而 UDP 支持**一对一、一对多、多对一和多对多**的交互通信（例如局域网内的广播、多播）。

​	由于其特性，UDP通常用于那些对实时性要求高但对可靠性要求不高的应用，例如视频流、VoIP（语音通信）、在线游戏、早期的聊天软件等。

## UDP 报文头结构

​	UDP 的首部格式极其简单，总共只有 **8 个字节**，由四个字段组成，每个字段 2 个字节（16位）。

![UDP头部格式](https://hixiaodong123.oss-cn-hangzhou.aliyuncs.com/typora/202504092051971.png#padding#600w)

| **字段名称**          | **长度 (bits)** | **主要功能简述**                                             |
| --------------------- | --------------- | ------------------------------------------------------------ |
| **源端口 (Source)**   | 16              | 标识发送该报文的应用程序端口号。在需要对方回信时使用，不需要时可全置为 0。 |
| **目的端口 (Dest)**   | 16              | 标识接收该报文的应用程序端口号。这在终点交付报文时必须使用。 |
| **长度 (Length)**     | 16              | 整个 UDP 数据报的长度（包括首部和数据部分），其最小值是 8（即只有首部，没有数据）。 |
| **校验和 (Checksum)** | 16              | 用于检测 UDP 数据报在传输过程中是否有错。如果有错，接收方会直接丢弃该报文。 |

## TCP 与 UDP 的核心区别

| **对比维度**           | **TCP (传输控制协议)**                                       | **UDP (用户数据报协议)**                                     |
| ---------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **连接状态**           | **面向连接**。传输前必须进行“三次握手”建立连接，结束后需“四次挥手”。 | **无连接**。随时可以发送数据，不需要建立和释放连接。         |
| **可靠性**             | **高度可靠**。保证数据不丢失、不重复、不乱序到达。           | **不可靠**（尽最大努力交付）。可能会丢包、乱序，不保证送达。 |
| **传输方式**           | **面向字节流**。将数据看作无结构的字节流，无边界。           | **面向报文**。保留应用层报文的边界，一次发送/接收一个完整报文。 |
| **通信对象数量**       | 仅支持 **一对一** 的点对点通信。                             | 支持 **一对一、一对多、多对一、多对多** 通信。               |
| **拥塞与流量控制**     | **有**。具备滑动窗口、拥塞窗口等复杂的控制机制。             | **无**。网络拥堵时不会降速，一直以恒定速率发送。             |
| **首部开销**           | 较大（至少 **20 字节**）。                                   | 极小（仅 **8 字节**）。                                      |
| **典型应用场景与协议** | 要求数据准确无误的场景。如：文件传输（FTP）、网页浏览（HTTP/HTTPS）、电子邮件（SMTP）。 | 要求通信速度和实时性的场景。如：语音/视频通话、直播、DNS域名解析、DHCP。 |
